**Observation:** the lane raised 3 🔴 tagged `[DECISION]`, 7 🟡 and 4 🔵, all on files shipped before v0.24.1, which cannot be edited (sqlx checks their checksum at start-up). Checked: the application runs sqlx 0.9.0, which wraps every migration in a transaction unless it opts out, and none of the eleven does — the two "no `BEGIN`/`COMMIT`" findings cause nothing. Decision (owner, 2026-10-10): a shipped migration is not judged again and an explicit transaction is not required; the rule goes into the `reviewer-sql` prompt. Left as debt: two foreign keys of `procedure_refund` and one of `bank_transfer` have no usable index (a new migration can add them; they matter only when a parent row is hard-deleted). One doubt that is more than form: before `20260316`, the transfer form stored `fund_<fund id>` or `patient_<patient id>` in `bank_transfer.source`. The migration built a link for every fund transfer by cutting that text at a fixed position, as if it were `fund_payment_group_<id>`, and dropped the column: a fund transfer recorded with the old form would have got a link to a group that does not exist, and a direct-payment transfer lost its patient reference. Whether any such transfer existed in a real database then is not known from here. The diagnostic report answers the first part without patient data: its foreign-key check counts the violations per table.

**Added 2026-10-11 (release sweep, the eleven files applied to a scratch database):** one correction — every foreign key of `bank_transfer` is indexed; the one without an index is `bank_fund_label_mapping.fund_id` (`20260308_init.sql`), which costs only on the hard delete of a fund. Two things tested, not seen on real data: the cash-account seed of `20260316_bank_manual_match.sql` (step 7) guards on `id` and not on the unique `name`, so a database from before March 2026 that held an active account named `Caisse` would refuse the migration and the application would not start; `20260524_billed_amount_not_null.sql` says in its header that deferred foreign keys make its table rebuild safe, which is false — it passes because the application migrates with foreign keys off (`db.rs`), and fails through the sqlx command line on any database with a payment. One doubt on data: step 2 of `20260522_add_fund_reconciliation_date_to_procedure.sql` cleared `confirmed_payment_date` on every procedure reconciled with its fund only, assuming it equalled the group's payment date, while the Excel import also wrote that column; only a copy from before the migration can say how many rows differed. The form findings on shipped files (a rename without an `-- IRREVERSIBLE:` marker, indexes without `IF NOT EXISTS`) fall under the decision above.
