# FLOW-079 — An entry's kind follows what a user sees, not who found it

- Kind: quality
- Size: S
- Observed: in the batch after 0.24.5, six bugs a user notices were filed as debt because a reviewer or `spec-checker` found them (DEBT-042, 045, 035, 046, 062, 063); `docs/workflow.md` § 2 already says a bug a user notices is a todo, and the filing followed the finder. The release then hit "no releasable commits" twice (FLOW-074, and v0.24.6 → v0.24.7).
- Proposal: the owner's, for this project as for another: TODO = what a user will see (a `feat` or a `fix`); DEBT = what a user will not see (`refactor`, `chore` on the application); FLOW = how the work moves (`docs`, `chore`, `ci`), no application code. Two edges: a document about the application (spec, contract, glossary) drifting from code that is right is DEBT, gated "when next touched" by default so it rides with the next `feat` or `fix` of that area — alone only when it blocks something; tooling code (`scripts/`, the `justfile`, hooks, workflows) is FLOW. A todo the agent files waits for the owner's confirmation of its User value before it is queued (FLOW-068). Existing entries are not re-sorted.
- Costs: the § 2 "Filing an entry" wording and `/file-entry`'s kind step, both at their ceiling. Protects: a queue whose kinds predict its changelog — no TODO, no releasable commit.
- Decision (owner, 2026-10-17): "TODO = user will saw something (fix or feature). DEBT = refactor, chore, user will not saw anything. FLOW = mainly doc, chore, ci: no code change (but ci stuff)"; a document update stands alone only as DEBT with a gate ("ok go with debt + gate, record it").
